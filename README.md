This project is a small collection of lockless (and wait free) concurrent data structures:
a stack, a fixed sized hash-map and the star of the show, a resizeable hash-map, complete with memory reclamation.

The stack and fixed sized hash-map are simple enough I won't go into depth about their inner workings, but I will for the resizeable hashmap.

First, the scope: I want this map to be akin to a typical C++ data structure in design that also happens to support lockless operations. This means it should take arbitrary types for the key and values, it should not be a singleton, and it should own all the data it needs.

A very important question when making a hash-map is whether it should use open addressing or separate chaining. There are generally performance benefits to open addressing, but I picked it because lockless operations on an array seemed less daunting than arbitrary deletions in a linked list (and I didn't want too stray as far from standard designs as to use an array per node). 

However, due to wanting to support keys of arbitrary size, I store the hash, key and value as a heap object so that I can just have the map operate on the pointer, potentially undoing the performance benefits of open addressing. 

To handle the state of elements in the map (moving, deleted, active), I packed the bottom 2 bits (the bottom 3 are fine to pack because of the alignment of the hash). Deletions are therefore handled by just marking the bottom bit.
I chose not to handle reusing deleted slots since it could create issues with duplicate insertions if a thread is above to insert in a slot but is put to sleep, then an earlier element is removed and then a new element with the same key as is being inserted is inserted in that earlier slot, then when the first thread wakes it'll insert a second element with the same key. I just let the resizing handle the space taken up by removed items.

To reduce cacheline contention, the elements in the array are aligned at `std::hardware_destructive_interference_size` (although by default it is 256bytes on Apple Clang for Apple silicon despite Apple silicon using 128 byte cachelines).

The key to the design is the use of 2 arrays and treat both as valid for the purpose of retrieval while moving items across as new ones are inserted only into the "new" array. 

After a resize has taken place, every item in the map is in the "old" array. When a thread tries to insert new data into the array, it first increments a counter for how far along the old array has been moved by 16. It then searches those 16 slots in the old array and moves all the alive items, marking each of them as being moved before moving, and marking them as dead after being inserted. When moving, it only inserts into the new array if it doesn't see the key in the new array, regardless of the state of that element since the new array always has newer data than the old array.

When the thread completes the move of its elements, it marks a slot for said 16 elements in the array to true and then begins inserting its actual data into the new array. It probes from the start for that hash until it either finds an empty slot or a slot with the same key (which is found with first a check that the hash matches to short circuit in case the key's operator== is expensive to compute) in which case it will insert the new data there. It, naturally, inserts with an atomic compare swap. 

The remove method probes through the new array. If it finds the key, it marks it as deleted and returns. If it doesn't find the key in the new array, it searches through the old array. If it sees the item with the correct key and it is not marked as being moved, it marks it as deleted and returns. If it sees the correct key and it is being moved, it marks it deleted in the old array and then tries to inserts a, pre-deleted, element into the new array. If the deleting thread beats the moving thread to inserting the element, the moving thread leaves it as is. 

A common data structure I used in this project is what I have later learnt is called a hashed striped counter. Where a counter (or other data) is stored in a fixed sized hashmap based on a hash of the thread's id. This reduces contention of cachelines. Without a specific use case for this map in mind, I decided to impose no requirements for threads to separately store data for this map, nor require it to be a singleton, and nor to make any assumptions about the amount of and longevity of threads. I used this to decide when to resize: there is a per array overestimating counter for the amount of elements in this map. A thread increments it by a number (16 in this case) and then banks those 16 inserts in its per thread hash count, reducing contention of the map counter by a factor of 16. Due to it needing to be checked less, deletions are just counted per thread hash. When the overestimating counter reaches more than 50% of the array's capacity (to minimise long probe chains), a resize is called. Because deletions do not free up space, if inserts and deletions occur at a similar rate, a similar amount of data needs to be stored, not an ever increasing amount as like what std::vector's resize is designed to allow for. As a result, a resize only doubles the size of the new array if deletions are less than half of the array's data, the new array is the same size if deletions are between half and three quarters and if more than 3 quarters, the new array size is halved. So that a long running map is not holding onto memory it hasn't needed in a long time. 

Naturally, my requirements are that if only one thread is modifying a specific key, it should act like a single threaded map. Meaning all 3 operations need to show no effects of an ongoing resize, including that a get operation must return the value throughout the entire resize and an element cannot come back from a deletion through a resize, tricky but solvable. If multiple threads operating on the same key at the same time, the end result is unspecified.

Initially, I was conservative with reading the pointer to both arrays for non-modifying operations (get and removals for non-present keys) on the grounds that it's fine if it reads slightly older data, given prior operations from the same thread would be operating on the same data. This became too difficult to properly reason about and so now, before any operation returns, it checks if it has been looking at the most up to date arrays, and if not, it calls the function again. So that an operation only finishes when it has operated on the most up to date data.

The final challenge was memory management and reclamation. Should be easy, `std::shared_ptr` exists... oh, basically only `const std::shared_ptr` is valid in the "critical section". Ah well there's `std::atomic<std::shared_ptr>`... which uses a lock (spinlock included). Well it's 2026 so that means I can use C++26's `std::harzard_ptr` for exactly this... but there's zero mainstream compiler support. It would defeat the point of this to use a third party library so I'll do it myself. 

Before considering reclamation, it's good to consider how the data should be allocated in the first place. Given deleted items need to stay allocated so their keys can be checked, many objects become deallocatable together once the old array is disconnected from the map, so an arena is well suited to this. I want the map to be able to grow and shrink to whatever size is required. And so, instead of reinventing the wheel I allocate in batches with new and then use delete when the arena is deletable, instead of mostly recycling memory manually and designing some system to occasionally give back memory to the OS, I let new/delete handle that behind the scenes, despite that making it not truly lock free. The memory is stored in per type linked arrays. To handle allocation of arrays, the size of these linked elements can vary. When a request to allocate more sequential items than there is space for in that node, a new node is created and, for simplicity, the previous node is no longer allocated into. To reduce contention, these linked arrays of memory are per-thread, stored in an seperate chaining, fixed sized array based hashmap on the thread's id. For a given hash, there is a linked list of seen threads for that hash. The thread id and next pointer elements of each node need to be read by multiple threads but anything else is only for a single thread, so I made the thread id and next pointer their own cacheline so there would be no contention for the rest of the data, while still storing it inline. The arenas do call the destructors on the types if they have one (for simplicity the arenas do return void * to uninitialised memory so it is up to the user to initialise the memory, else the destructor will be called on it), but types with trivial destructors are preferred to minimise the latency spike of this operation. 

The key thing for memory reclamation is for a thread to be able to mark a value as being used before accessing the desired data and that the memory to mark mustn't be deallocated. Given we are using arenas anyway, I settled on an epoch based design. Before any operations on the map can happen, a thread must request a token for the map in its current state that, while the token isn't destroyed, prevents deallocation of that memory. Given I want the memory reclamation to be entirely per map, a thread local epoch value would not suffice. I chose to store 3 of the arena structures and for each hash of each arena structure, there is also a count of the active threads, which is incremented and decremented. Typical epoch based reclamation systems have a single "active" epoch where all the elements attached to the main structure are in. That doesn't really work when the old and new arrays both need to be active but can be on different epochs. So in addition to the hashmap that contains active threads, there is a perpetual users count which is incremented when an array is attached to the map and decremented when disconnected (since other threads won't be waiting on deallocation, the thread that atomic compare swaps the pointer to arrays is responsible for incrementing and decrementing these counts (its possible for this count to be negative if the thread sleeps after the successful cas, but that's fine because that thread's using token must be active while it sleeps). When resizing, the epoch is attempted to be advanced by 1 and succeeds if the next arena isn't being used by any threads, in which case that thread deallocates the memory for that arena and then advances it. This does mean that arenas are deallocated in the same order as how they are used which means that a token for a specific arena is valid for all future arenas. The map therefore returns a token for the arena of the old array. New allocations always use the "active" arena meaning the elements in an array can be allocated in a newer arena than the array, but that's fine. 

So there you have it, a wait-free resizeable hashmap that reclaims memory.

This has been my first experience with lockless programming with atomics and it's just been fun. I've quite enjoyed working around the limitations with creating complex data structures where every step of every operation needs to leave the structure in a valid state. I spent a lot of time going about my day thinking and mentally designing these data structures, which I quite enjoyed. Additionally, I really like how lockless programming forces thinking about code as running of real specific hardware instead of an abstract machine, with considering the memory ordering that's particularly important to Arm but is far more generous on x86, compare exchange strong and weak (and finding out that it's because weak compare exchange on Arm works by just checking if the cache line has been interrupted), and the performance implications of double word loads and stores. The memory ordering in particular (well specifically how x86 achieves good performance while using strong ordering) has, in addition to my prior experience with Arm and x86 SIMD, given me real appreciation for current x86 processors, despite high end Arm processors beating them in single threaded performance in Geekbench and Spec. It is interesting to finally see examples of how x86 as an instruction set can be better suited to HPC relative to Arm (well I just mean Arm and x86 as is commonly implemented for SIMD [I really want to use the Fujitsu A64] and how strong ordering encourages x86 chips to be better handle core to core communication).

This project has been a great example of using AI for learning. All the code and designs where self-developed (the key idea of resizing was based on a conversation I had 6 months prior about something in a database implementation, and then I spent time thinking about how it could work) but everything I learnt for this was from an LLM (mainly Gemini 3.1 Pro actually, the prevailing sentiment which I agree with is that Gemini models are bad for coding, but I've found Gemini 3.1 Pro to be very good for information gathering, better than other models in Perplexity, and in agreement with Artificial Analysis' Omniscience benchmark where Gemini was only beaten by Opus 5 and above and GPT-6 Astra, despite Gemini 3.1 Pro being several months older). The standing that linked lists have occupied in my opinions has shifted quite a bit from this project. A linked list was the first abstract data type I learnt about and it was useful in C, being an easy way to store data of an unspecified amount, but is much less useful compared to the generally much more performant resizeable arrays built into most languages. I've of course been aware of the time complexity benefits for inserting and removing from the middle and how linked lists are used in operating systems and the like, but until this project I haven't felt the benefits myself (the last time I really used linked lists was finding iteration is between 5 and 500 times slower than an array [nodes are allocated sequentially comapred to random allocations where everything is a cache miss]). In concurrent programming however, a linked list, particularly with insertions and deletions at the head, becomes a clear default due to not having to resize. I also think it's notable how effective use of linked lists in general is subtly less OOP than other structures. That in an intrusive linked list, the list object doesn't create it's nodes and that nodes need to use non-owning pointers to each other, else stack overflow for long lists. 

I feel writing this code in an object oriented style was a mistep and I think explicitly passing state would be a better strategy. I wanted to control the amount of loads to the main object's data and so I'd either have to create static functions and pass in the loaded state then and there or make parts of that loaded state their own objects. However, aspects that should be encapsulated to these inner classes (like iterating the count of the items) need to enact things for the whole map (like resizing), meaning all of these inner classes need references to the wider map, something that I would say is conceptually acceptable because that's how Java inner classes work by default, but it certainly looks bad in C++. A deeper issue is how OOP's abstractions just seem unideal for lockless concurrent programming (they are very well suited to mutex based concurrent programming). A small example is how after calling a method which happens to load data, it was better to do a relaxed load, and I feel that is poor encapsulation. 

While the challenge is part of the point for me, pinning cores to a specific process and entirely disabling interrupts in kernel-space does sound quite appealing, for a spinlock to be able to be guaranteed to be for a small maximum number of cycles.

The most difficult part of this project was honestly the testing. It's not really that I spent a long time testing, but coming up with good realistic tests when I don't really have use case for this in mind would be a chore, so my testing is honestly quite limited.
